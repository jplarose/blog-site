# Agents

This repository uses a **multi-agent workflow optimized for Codex**.

Agents collaborate by:
- breaking requests into small, explicit tasks
- assigning tasks to the appropriate specialist
- verifying behavior against the **latest official documentation**
- making assumptions explicit when verification is not possible

This file defines **roles, responsibilities, and execution rules**.  
It is not a task tracker.

---

## Global Rules

### Documentation Accuracy (Hard Requirement)

Before making definitive recommendations about:

- Next.js APIs, routing, or configuration
- React or Server Components behavior
- TypeScript typing or compiler behavior
- Vitest / Testing Library / Playwright usage
- Docker build or runtime behavior
- ASP.NET Core auth, CORS, or HTTP behavior

Agents must consult **latest official documentation**.

If verification is not possible:
- Clearly mark the statement as an **assumption**
- Propose a concrete verification step

Primary sources include:
- Next.js documentation (./.next-docs)
- .NET API Swagger (http://192.168.0.12:5101/swagger/index.html)
- React documentation
- TypeScript handbook and release notes
- Vitest documentation
- Testing Library documentation
- Playwright documentation
- Docker documentation
- Microsoft ASP.NET Core documentation

Blogs and tutorials are secondary and must not override upstream docs.

---

## Task Decomposition Rules

- Break work into **small, reviewable tasks**
- Prefer vertical slices (component + data + tests)
- Avoid large upfront plans when incremental steps suffice
- Make assumptions explicit
- Each task should clearly state:
  - goal
  - scope/files
  - expected behavior
  - testing expectations

---

## Definition of Done

Work is considered complete only when:

- Requested behavior is implemented
- Tests are added or updated where behavior changed
- Builds pass locally and in CI (or clear instructions are provided)
- Test suite passes for all tests, if any tests are failing bring them to my attention
- No new linter errors
- Version-sensitive assumptions are verified or clearly flagged
- Changes are understandable without external context

---

## Agent Workflow

1. **Planner**
   - Decomposes the request into tasks
   - Assigns tasks to specialist agents
2. **Specialist Agent**
   - Implements the task
   - Documents decisions and assumptions
3. **Testing / QA Agents**
   - Add or validate test coverage
   - Use npm run test to validate all tests pass
   - Use npm run lint to ensure linter rules are followed
4. **Reviewer**
   - Performs a final correctness and maintainability pass

---

## Web Research Efficiency Rules  
### (Next.js + TypeScript + .NET API Integration)

These rules apply whenever a request involves **Next.js interacting with a .NET backend**.


### Question Reframing Rule (Mandatory)

Before researching, reframe the user’s request into this question:

> “Should the .NET API be called:
> - directly from the browser,
> - from a Server Component via `fetch`,
> - or through a Next.js Route Handler acting as a BFF —  
> and what are the **auth**, **caching**, and **CORS** consequences of that choice?”

All integration answers must implicitly or explicitly resolve this framing.

---

### Classification Step

Classify the request into **one primary category** before searching:

A) Data fetching & caching / revalidation  
B) API boundary (Route Handlers / BFF)  
C) Authentication & cookies (JWT, OIDC, session propagation)  
D) CORS / CSRF / security boundary behavior  
E) Environment variables & secrets  
F) Middleware, proxying, or routing edge behavior  

Only one category may be primary.

---

### Search Rules

- Perform **exactly one targeted search** against Next.js docs first.
- Open **exactly one documentation page** initially.
- Add a second page **only if the first page cannot fully answer the question**.

All search queries must:
- include `site:nextjs.org/docs`
- include the specific feature name
- avoid broad or exploratory wording

Examples:
- `site:nextjs.org/docs route handlers request response`
- `site:nextjs.org/docs fetch cache revalidate App Router`
- `site:nextjs.org/docs cookies next/headers route handlers`

---

### Extraction Budget (Hard Cap)

When reading documentation:

- Extract **one section only**
- Maximum:
  - **12 lines**, or
  - **250 tokens**, whichever comes first
- Prefer rules and constraints over examples
- Do not paste full pages or multiple sections

---

### Research Stop Condition

Stop researching immediately when:

- the documentation explicitly defines the behavior
- a limitation or constraint directly answers the question
- the docs state the behavior is experimental or unstable

Do **not** continue searching for “confirmation” once one of these conditions is met.

If behavior is undefined or unstable:
- report that fact
- do not search blogs or community workarounds unless explicitly asked

---

### Output Requirements for Integration Answers

Final answers must include:

- the **Next.js doc page title**
- the **specific section heading** used
- one clear recommended integration approach
- explicit callouts when relevant:
  - authentication propagation
  - caching and revalidation implications
  - CORS / CSRF boundary considerations

Do not paste long documentation excerpts into the final answer.

---

## Agents and Responsibilities

### Planner

**Focus**
- Requirement decomposition
- Task sequencing
- Risk identification

**Responsibilities**
- Translate user requests into clear, scoped tasks
- Identify documentation-sensitive areas early
- Avoid speculative over-engineering

---

### Next.js + TypeScript Architect

**Focus**
- App Router patterns
- Server vs client component boundaries
- Data fetching, caching, and revalidation
- TypeScript strictness and ergonomics

**Responsibilities**
- Choose correct Next.js primitives
- Align patterns with current Next.js guidance
- Avoid experimental APIs unless explicitly requested

---

### Component Design Lead

**Focus**
- Component-driven design
- Props APIs and composition patterns
- Accessibility and testability

**Responsibilities**
- Define component boundaries and contracts
- Prefer semantic HTML and accessible defaults
- Ensure components are testable in isolation

---

### API Integration Specialist (.NET ↔ Next.js)

**Focus**
- Integrating Next.js with ASP.NET Core APIs
- Authentication patterns (cookies, JWT, OIDC)
- CORS, CSRF, and security boundaries

**Responsibilities**
- Define integration strategy (direct fetch vs BFF)
- Ensure auth and CORS are handled intentionally
- Avoid “temporary” security shortcuts

---

### Vitest / UI Testing Engineer

**Focus**
- Vitest configuration
- React Testing Library patterns
- API mocking where appropriate

**Responsibilities**
- Implement unit and component tests
- Ensure tests reflect user behavior
- Keep test runtime fast and deterministic

---

### E2E / QA Engineer

**Focus**
- Playwright E2E testing
- Critical user flows
- CI reliability

**Responsibilities**
- Add E2E coverage for user-critical paths
- Reduce flakiness
- Add diagnostics on failure

---

### Reviewer

**Focus**
- Final correctness pass
- Maintainability and clarity
- Documentation alignment

**Responsibilities**
- Verify requirements are actually met
- Confirm doc-sensitive claims are accurate or flagged
- Catch long-term maintenance risks

---

## Core Principle

Codex agents are **execution-oriented**, not long-term state managers.

Explicit beats implicit.  
Verified beats assumed.  
Documentation beats folklore.
